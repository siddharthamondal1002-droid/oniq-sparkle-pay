### The promise that constrains the AI phase

`src/routes/privacy.tsx` line 152 says, in bold: **"Health data is never sent to any AI feature."** `src/data/__tests__/playCompliance.test.ts` ("says health data never reaches a model, and means it") verifies it by scanning every edge function for `health_checkins|cycle_logs|health_profiles` and requiring zero matches.

So two things follow for ONIQ Health:

1. Phase 1 may not reference those three table names from any edge function (it does not; Health has its own tables).
2. **`health.ai.enabled` cannot be turned on without first changing the public privacy notice and the Play Data safety form.** That is a user-visible policy change and belongs to the owner, with counsel. The architecture document records the exact wording that has to move.

**Superseded 2026-09-09 (owner directive).** The sentence is now the consent-conditioned statement in `src/config/privacy.ts` (`HEALTH_AI_PRIVACY_STATEMENT`), rendered in the notice, beside the AI consent in English, Hindi and Bengali, and mirrored in the Play declaration; `src/health/__tests__/privacyDisclosure.test.ts` keeps the retired claim out of every user-facing source and ties the new statement to the controls it names. Measured the same day: the report scan above IS configured in production (`ANTHROPIC_API_KEY` present — an authenticated call with an empty attachment answers 400 rather than `configured: false`), so an uploaded report reaches Anthropic today, with no consent step; the old sentence never covered it and the new one does not name it. Counsel's — `04 D4`.

## 4. Feature flags, i18n, doors

- Flags are compile-time `export const` booleans in `src/lib/flags.ts` (plus the `ATTACH_FLAGS` record). Server-side kill switches are config rows (`video_gen_config`). Health follows both: `src/health/flags.ts` (client, all `false`) and a `health_config` row (server, all `false`, fail closed when absent).
- i18n: `src/lib/i18n/dictionaries.ts` carries `en`, `hi`, `bn` and ten more; `registerTranslations()` lets a screen add its own namespace; `useT()` resolves. Tile names live in `tileLabel.ts` (`TILE_LABELS`, `TILE_LABELS_HI`). Health strings are registered for **en, hi, bn** as the prompt asks.
- Doors: Home tile (`worlds.ts`), icon (`worldIcons.tsx`), bottom nav (`app.tsx` `NAV_WORLDS`), site card (`marketingCopy.ts`), Play line (`playCompliance.ts`), mini-app registry. `upiDoors.test.ts` is the lesson: enumerate every door and evaluate the app's own expressions. Health's doors are pre-wired and gated on one flag; `healthDoors.test.ts` proves they are shut and that they would open.

## 5. Notifications

`send-push` (FCM v1) carries the sender name and a `preview` of the message in the notification body. A health notification must never carry a value, a diagnosis, a document title or a record kind. Phase 1 sends none; the isolation guard fails if `send-push` or `push.ts` learns a health kind.

## 6. Environments

There is **one** production Supabase project and **one** Firebase/GCP project. The Supabase project the owner's own credential can see (`nzbthoecadcwdoqxhaok`) is _not_ ONIQ (see CLAUDE.md, "Two Supabase projects"). There is no staging. Dev/staging/prod separation for health data therefore does not exist today; it is a decision (a second GCP project for Healthcare API datasets at minimum), listed for the owner.
